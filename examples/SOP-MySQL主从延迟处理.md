# SOP-MySQL 主从延迟处理

适用范围：一主多从架构，延迟指 `Seconds_Behind_Master`。

## 1. 告警定义
- 延迟 > 30 秒持续 5 分钟：观察并记录。
- 延迟 > 300 秒持续 5 分钟：介入处理，存在读脏数据风险。
- 延迟 > 1800 秒：立即升级，并考虑摘除该从库读流量。

## 2. 影响面确认
- 该从库是否承载读流量，摘除后剩余从库能否承受读压力。
- 是否有依赖该从库的报表、同步任务或数据抽取任务。
- 主库当前写入量是否异常（对比同时段历史基线）。

## 3. 快速定位

### 3.1 确认延迟真实值
`Seconds_Behind_Master` 在大事务场景下会被高估。先在从库执行：

```sql
SHOW SLAVE STATUS\G
```

关注 `Slave_IO_Running`、`Slave_SQL_Running`、`Seconds_Behind_Master`、
`Relay_Master_Log_File` 与 `Exec_Master_Log_Pos` 的推进情况。
若位点持续推进，说明只是追不上，不是卡死。

### 3.2 判断卡在哪个环节
- IO 线程异常：多为网络抖动、主库连接数打满或 binlog 被清理。
- SQL 线程异常：多为从库执行报错（主键冲突、表不存在、DDL 不兼容）。
- 两者正常但延迟高：多为大事务、从库资源不足或缺少索引。

### 3.3 常见根因
- 主库执行了大事务（批量 UPDATE / DELETE、大表 DDL）
- 从库规格低于主库，或存在其他重查询抢占资源
- 表缺少主键或索引，导致从库回放时全表扫描
- 从库上有长事务或慢查询阻塞回放

## 4. 处置步骤
1. 摘除该从库的读流量，避免业务读到旧数据。
2. 找到阻塞源：在从库执行 `SHOW PROCESSLIST`，定位长事务并评估是否可 kill。
3. 若是大事务导致，等待其回放完成，期间不要反复重启复制。
4. 若 SQL 线程报错且明确为可跳过错误（如已确认的重复主键），按变更流程评估后处理，**不得直接跳过未知错误**。
5. 延迟回落后恢复读流量，先放 10% 灰度观察 5 分钟。

## 5. 禁止操作
- 禁止在未确认数据一致性的情况下，把延迟中的从库提升为主库。
- 禁止在从库上直接写入业务数据，会造成复制冲突。
- 禁止用 `SET GLOBAL sql_slave_skip_counter` 盲目跳过错误。

## 6. 恢复后必做
- 用 `pt-table-checksum` 或业务侧对账校验主从一致性。
- 在复盘记录大事务来源，推动改造为分批执行（建议单批不超过 5000 行）。
