# SOP-主机资源异常处理

适用范围：所有生产 / 预发环境的 Linux 实例（容器与物理机通用）。
原则：**先止损，再定位根因；先摘流量，再保留现场。**

## 1. CPU 使用率过高

告警阈值：5 分钟内平均使用率 > 85%，持续 10 分钟未恢复则升级。

### 1.1 快速定位
- 确认告警范围：单实例还是多实例。多实例同时超标通常是流量或上游依赖问题，单实例多为实例自身异常。
- 执行 `top -c` 按 CPU 排序定位进程，记录 PID。
- 对 Java 进程执行 `jstack <pid> > /tmp/jstack.txt` 连续抓 3 次，间隔 5 秒。
- 查看该实例近 30 分钟是否有发布、配置变更、定时任务。

### 1.2 常见根因
- 业务流量突增（大促、刷量、上游重试风暴）
- 死循环或正则回溯（常见于新上线的文本处理逻辑）
- JVM GC 频繁（堆内存不足或存在内存泄漏）
- 宿主机超卖导致 steal time 偏高

### 1.3 处置步骤
1. 摘流量：将该实例从负载均衡摘除，避免影响面扩大。
2. 保留现场：抓 jstack / perf top / 火焰图后再重启。
3. 重启进程恢复服务，确认监控回落。
4. 事后补齐：定位到具体代码或配置后提交修复，并在复盘记录触发条件。

### 1.4 禁止操作
- 禁止在未保留线程栈的情况下直接重启，会导致根因无法复现。
- 禁止在生产实例上执行 `kill -9` 后不摘流量，会造成请求批量失败。

## 2. 内存使用率过高

### 2.1 快速定位
- `free -h` 确认是应用占用还是缓存占用，buff/cache 高不属于异常。
- `ps aux --sort=-%mem | head` 找出占用最高的进程。
- 容器环境需确认是否已触发 OOM Killer：`dmesg | grep -i oom`。

### 2.2 处置步骤
1. 若已 OOM，先确认进程是否被自动拉起，未拉起则手动启动。
2. 临时调大堆内存上限（不超过容器 limit 的 70%）。
3. 若存在内存泄漏趋势（持续上涨不回落），安排灰度回滚至上一版本。

## 3. 磁盘空间不足

告警阈值：使用率 > 85%。

### 3.1 快速定位
- `df -h` 确认告警挂载点。
- `du -xh --max-depth=2 /data | sort -rh | head -20` 定位大目录。

### 3.2 可安全清理
- 已轮转的归档日志（`/data/logs/*.log.*.gz`）
- `/tmp` 下的临时文件与超过 7 天的 core dump
- 包管理器缓存、容器悬空镜像

### 3.3 禁止操作
- 禁止删除未备份的业务数据。
- 禁止直接 `rm` 正在被进程写入的日志文件，应先用 `truncate` 或 `: > file` 清空句柄，否则空间不会释放。

### 3.4 升级条件
清理后可用空间仍低于 15%，或增长速度超过 10GB/天，转存储组扩容并同步值班经理。
