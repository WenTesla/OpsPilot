# OpsPilot v0.2 设计文档：接入 MCP 活数据

> 版本目标：**让 Agent 从"只读文档的问答助手"变成"能查线上现状的排障助手"。**
> 对接自然语言仍走 `/api/chat`，知识库（RAG）保持不变，新增的是「查活数据」这一路能力。

---

## 1. 背景与目标

### 1.1 v0.1 的瓶颈

v0.1 的能力边界很清楚（`backend/app/agent/graph.py`）：

```
用户提问 → Agent → 唯一的工具 search_ops_knowledge（RAG） → 组织答案
```

它只能回答"SOP 上写了什么"，回答不了"现在怎么样"。典型失败case：

| 用户问 | v0.1 表现 |
|---|---|
| 「order-service 现在 CPU 多少？」 | 去翻 SOP 文档，答非所问或直接说知识库未覆盖 |
| 「刚才那批 504 是不是数据库慢导致的？」 | 无法验证，只能给出通用排查步骤 |
| 「这个告警要不要立刻止损？」 | 没有实时数据支撑，给不出判断依据 |

根因不是模型不够强，是 **Agent 手上没有第二个数据源**。LangGraph 的 `ToolNode` 本来就是为多工具设计的，v0.1 只用了一个。

### 1.2 v0.2 目标

一句话：**在不动 RAG 主线的情况下，给 Agent 挂上一组只读的线上数据工具（指标 / 日志 / 告警 / 服务信息 / 历史故障），并让它优先用活数据验证、用知识库兜规范的 SOP。**

三条可验收的硬指标：

1. **能回答现状类问题**：问「xx 服务最近 30 分钟 CPU 怎么样」，Agent 能调用 `query_metrics` 并给出带数值、带阈值的结论（而不是去翻文档）。
2. **能交叉验证**：问故障时，Agent 的典型行为变成「先查告警/指标定位现象 → 再查 SOP 要处置步骤」，一次会话里出现 **≥2 次工具调用**。
3. **降级不破功**：没装 MCP 依赖、或 MCP 服务没起来时，系统**完全退回 v0.1 行为**，现有 4 份示例文档的问答与评测（`eval_rag.py`）结果不回退。

### 1.3 非目标（本次明确不做）

| 不做 | 原因 | 留给 |
|---|---|---|
| 任何写操作类工具（重启、扩容、回滚） | 需要分级护栏、dry-run、审批，是一整套独立设计 | v0.4 |
| Plan-Execute-Replan 编排重构 | 先把工具有了，再改编排才有意义；两个变量一起改无法定位问题 | v0.3 |
| Milvus / Neo4j / Kafka | v0.1 的 numpy 索引还远没到瓶颈 | v0.4+ |
| 真实 Prometheus / CLS SDK 对接 | 依赖真实环境凭证，无法在任何人机器上跑通 | 保持 Mock 数据源 + 留适配层 |

│     • search_ops_knowledge        • list_services              │
│       （RAG，保持不变）            • get_service_info           │
│                                   • query_metrics              │
│                                   • list_active_alerts         │
│                                   • search_logs                │
│                                   • get_error_breakdown        │
│                                   • search_incident_cases      │
│              │                           │                     │

### 2.3 一次提问的完整时序（目标行为）

```
用户：order-service 最近半小时是不是有问题？

1. agent   → list_active_alerts(service="order-service", since_minutes=30)
             ← 返回 2 条告警：HighErrorRate(critical)、LatencyP99 超阈值
2. agent   → query_metrics(service="order-service", metric="error_rate", minutes=30)
             ← 返回 p95=7.2%，阈值 1%，确认劣化
3. agent   → search_ops_knowledge(query="order-service 5xx 错误率飙升 处置")
             ← 返回《SOP-接口5xx错误排查》第 2 节（带 [1] 引用）
4. agent   → 生成答案：现象（活数据）+ 处置步骤（知识库，带引用）

前端：工具调用气泡 × 3 + 正文 + 引用卡片（文献类与数据类分色展示）
```

## 3. MCP 工具契约

### 3.1 四条设计原则

1. **只读**：方法语义限定为 `list / get / query / search`。**禁止**出现 `restart / scale / rollback / exec / delete`。这是 v0.2 的安全红线，靠代码 review 与工具名白名单双重保证。
2. **窄参数**：每个工具参数 ≤5 个，能不给就不给。时间统一用**相对分钟数**（`minutes=30`）而非绝对时间戳 —— LLM 算时间戳极易出错，实测会把时间填成未来导致返回空；需要绝对时间时由 server 侧自行换算并返回。
3. **小返回**：数据点默认截断到 **≤30 个点**（`max_points` 参数，server 侧硬上限 60）。LLM 不需要看 60 个浮点数，它需要的是 `avg / max / p95 / 是否超阈值` 这几个统计值 + 少量样本。
4. **可溯源**：每个返回体必须携带 `source` 字段，标明 server、tool、采集时间、**是否为 Mock 数据**。Mock 标记尤其重要 —— 否则演示时用户会把假数据当真相。

### 3.2 monitor_server（:8101/mcp）

| 工具 | 参数 | 返回要点 |
|---|---|---|
| `list_services` | `env: str \| None`（prod/stage） | `[{name, env, owner, replicas, status}]` |
| `get_service_info` | `service: str` | `{name, version, depends_on:[...], depended_by:[...], recent_changes:[{at, type, desc}]}` |
| `query_metrics` | `service: str`<br>`metric: cpu\|memory\|latency_p99\|qps\|error_rate`<br>`minutes: int = 30`<br>`interval: 1m\|5m = 1m`<br>`max_points: int = 30` | `{metric, unit, points:[{ts,value}], stats:{avg,max,min,p95}, threshold, alert_triggered, trend: up\|stable\|down}` |
| `list_active_alerts` | `service: str \| None`<br>`since_minutes: int = 60`<br>`severity: critical\|warning\|all = all` | `[{alert_id, name, service, severity, value, threshold, started_at, duration_min}]` |

> 相对 OneCall 的取舍：它按 `query_cpu_metrics` / `query_memory_metrics` 拆成多个工具，工具数会随指标线性膨胀、挤占提示词。这里合并成单个 `query_metrics` + `metric` 枚举参数，后期加指标只改枚举不动工具清单。
> `get_service_info` 返回的 `depends_on` / `recent_changes` 是特意保留的 —— 这是 v0.4 做知识图谱根因推理的现成数据源。

### 3.3 log_server（:8102/mcp）

| 工具 | 参数 | 返回要点 |
|---|---|---|
| `search_logs` | `service: str`<br>`keyword: str \| None`<br>`level: ERROR\|WARN\|INFO\|all = ERROR`<br>`minutes: int = 30`<br>`limit: int = 20` | `{total, samples:[{ts, level, message, trace_id}], top_patterns:[{pattern, count}]}` |
| `get_error_breakdown` | `service: str`<br>`minutes: int = 30` | `{total, by_type:{TimeoutException: 128, ...}, top_source, trend_pct_vs_prev}` |
| `search_incident_cases` | `symptom: str`<br>`service: str \| None`<br>`top_k: int = 3` | `[{case_id, title, symptom, root_cause, resolution, mttr_min, occurred_at}]` |

> `search_incident_cases` 是历史故障库查询，**先用 `examples/` 下的复盘文档做种子数据**（如"订单服务大面积超时"）。它是 v0.3「案例库沉淀」的前置接线口 —— v0.3 只是把数据源从静态文件换成每次排障落库的卡片，工具契约不变。

### 3.4 统一返回体结构

所有工具返回同一个信封，便于前端统一渲染、便于裁剪策略统一实现：

```jsonc
{
    "source": {
        "server": "monitor",           # 或 log
        "tool": "query_metrics",
        "collected_at": "2026-09-27 21:30:00",
        "mock": True,                  # True 时前端打「示例数据」灰标
    },
    "params_echo": {"service": "order-service", "minutes": 30},
    "data": { ... },                   # 各工具自有结构
    "hint": "",                        # 给 LLM 的补充说明，如「数据点已按 5m 聚合」
}
```

错误时**不抛异常**，返回同结构 + `"error": "..."` 文本。理由见 §4.7。

## 4. 接入实现

### 4.1 依赖

`requirements.txt` 追加（保持在「可选」区）：

```
langchain-mcp-adapters>=0.1.0    # MCP 工具 → LangChain 工具
fastmcp>=2.0                     # 仅本地 mock server 需要
```

必须**可选**：安装失败或缺失时，主服务照常启动（§7 降级矩阵）。这是本项目"零依赖能跑通"的底线。

### 4.2 配置（`app/config.py` + `.env`）

```python
MCP_ENABLED      = os.getenv("MCP_ENABLED", "auto")   # auto|1|0
MCP_MONITOR_URL  = os.getenv("MCP_MONITOR_URL", "http://127.0.0.1:8101/mcp")
MCP_LOG_URL      = os.getenv("MCP_LOG_URL",    "http://127.0.0.1:8102/mcp")
MCP_TIMEOUT_SEC  = float(os.getenv("MCP_TIMEOUT_SEC", "15"))
MCP_MAX_RETRIES  = int(os.getenv("MCP_MAX_RETRIES", "2"))
MCP_CONNECT_TIMEOUT_SEC = float(os.getenv("MCP_CONNECT_TIMEOUT_SEC", "3"))
```

`MCP_ENABLED=auto` 语义：能 import `langchain_mcp_adapters` **且**能连通（带 3s 握手超时）才启用。这样默认 `uv sync` 后没启 MCP 服务也不报错，体验和不加这个功能时完全一致。

### 4.3 `app/mcp/client.py` —— 单例 + 安全加载

```python
"""MCP 客户端：单例持有、失败降级、对外只暴露 load_tools()。"""
_client = None

def build_servers() -> dict:
    """按 settings 拼 MultiServerMCPClient 需要的 servers 字典。

    注意 transport 与 URL 必须匹配：
      本地 FastMCP 用 streamable-http（URL 形如 http://host:port/mcp）
      云端托管端点多为 sse（URL 形如 https://xxx/sse）
    两者写反会握手失败，且报错信息晦涩，故在此显式配置而非让库自动猜。
    """
    return {
        "monitor": {"transport": MCP_MONITOR_TRANSPORT, "url": MCP_MONITOR_URL},
        "log":     {"transport": MCP_LOG_TRANSPORT,     "url": MCP_LOG_URL},
    }

async def load_tools() -> tuple[list, dict]:
    """返回 (tools, status)。任何异常都吞掉，退化成 ([], {"enabled": False, "reason": ...})。"""
    ...
```

三个必须踩过的坑（来自 OneCall `app/agent/mcp_client.py` 的实践）：

1. **`MultiServerMCPClient` 自 0.1.0 起不再是上下文管理器**。写成 `async with MultiServerMCPClient(...) as c:` 会直接报错，必须 `c = MultiServerMCPClient(servers)` 后直接 `await c.get_tools()`。
2. **连接失败会以 `ExceptionGroup` / `TaskGroup` 形式抛出**，直接 `except Exception` 打印出来是一坨看不出根因的嵌套。要递归展开 `__cause__` / `exceptions` 链（参考 OneCall 的 `format_exception_chain`）。
3. **`get_tools()` 每次调用都会新建连接**。必须模块级单例缓存，否则每轮对话握手一次，延迟从 200ms 涨到秒级。

### 4.4 `app/mcp/tools.py` —— 白名单与裁剪

```python
TOOL_WHITELIST = {          # 不允许出现的动词，命中即丢弃该工具
    "restart", "scale", "rollback", "exec", "delete", "update", "kill", "deploy",
}

def filter_tools(tools: list) -> list:
    """按白名单 + 只读前缀过滤，并对同名工具做 server 前缀消歧。"""
```

- **只读校验**：函数名以 `list_/get_/query_/search_` 开头，或命中黑名单动词则丢弃。这是 §3.1 红线的代码落实 —— 将来有人往 server 里加了写操作工具，主服务也不会把它暴露给 LLM。
- **同名消歧**：两个 server 若都定义了 `get_service_info`，后加载的会静默覆盖前一个。统一改写为 `<server>__<tool>` 并在 docstring 首行标注归属。
- **docstring 长度**：MCP 工具的原始 docstring 常常几百字（OneCall 的 `query_cpu_metrics` 写了 50 行返回值说明）。全部塞进 prompt 会显著挤占上下文，这里统一截断到 **≤400 字符**，只保留语义描述与关键参数。

### 4.5 `app/agent/graph.py` —— 注入工具

改动极小，`OpsPilot.__init__` 增加可选参数：

```python
class OpsPilot:
    def __init__(self, pipeline: RAGPipeline, extra_tools: list | None = None):
        self.pipeline = pipeline
        self.tool = build_rag_tool(pipeline)
        self.tools = [self.tool] + (extra_tools or [])   # RAG 工具永久排第一
        self.model = get_chat_model().bind_tools(self.tools)
        self.graph = self._build()
```

`app/main.py` 启动时：

```python
mcp_tools, mcp_status = asyncio.run(load_tools())   # 失败则 [] ，不阻塞启动
agent = OpsPilot(pipeline, extra_tools=mcp_tools)
```

**RAG 工具保持第一位**，原因有二：一是 Mock 模型（见下）固定取 `tools[0]`；二是保证"先查规范、再谈处置"的默认倾向不被活数据冲淡。

### 4.6 Mock 模型适配（必做，否则演示是坏的）

`app/agent/llm.py` 的 `MockChatModel` 有两个硬编码行为会卡死 v0.2：

- `_next_message` 第一轮只调 `self.tools[0]`（恰好是 RAG 工具，蒙对了）；
- **第二轮只要看到 `ToolMessage` 就直接汇总成答案**，不会再发起第二次工具调用 —— 也就是说 Mock 模式下 Agent 永远只会调一次工具，目标行为（先查指标再查 SOP）根本出不来。

改法（低成本）：给 Mock 模型加一层**关键词路由**，让它先按意图挑工具，第一轮最多发两个调用：

```python
KEYWORD_ROUTES = [
    (("cpu", "内存", "负载", "延迟", "qps", "错误率", "指标"), "query_metrics"),
    (("告警", "报警", "alert"),                                "list_active_alerts"),
    (("日志", "报错", "堆栈", "exception"),                      "search_logs"),
    (("依赖", "拓扑", "谁调用", "上游", "下游"),                  "get_service_info"),
    (("之前", "上次", "历史", "复盘", "以前"),                    "search_incident_cases"),
]
```

命中则调对应 MCP 工具 + RAG 工具，**两轮后汇总**；未命中维持 v0.1 行为。这样在没有 API Key 的情况下（含 `eval_rag.py` 的 CI 环境）也能演示完整的多工具编排，不至于"功能做了但跑给人看时是个残废"。

> 注：`KEYWORD_ROUTES` 只存在于 Mock 模型内部，真实模型走正常的 function-calling，不受影响。

### 4.7 超时、重试与降级

| 层次 | 措施 |
|---|---|
| 单次调用 | 15s 超时，超时返回 `{error: "工具调用超时"}`，**不抛异常** |
| 瞬时失败 | 指数退避重试 2 次（1s、2s），参考 OneCall `retry_interceptor` |
| 整个 MCP 不可用 | `load_tools()` 返回空列表 → Agent 仅剩 RAG 工具 → 行为等同 v0.1 |
| 单工具不可用 | 该 server 加载失败只丢该 server 的工具，另一个照常可用 |

**为什么工具报错必须是返回字符串而不是抛异常**：`/api/chat` 是 SSE 流，异常会让整条流在 `_chunk_text` 处中断，前端表现为"回答到一半卡住"，且 `finally` 里的引用收集逻辑也走不到。返回错误文本则 LLM 能读到"这个工具现在不可用"并自行改走别的路径 —— 这才是 Agent 该有的健壮性。

### 5.1 SYSTEM_PROMPT 增补（关键）

现有提示词第 1 条写死了「必须先调用 `search_ops_knowledge`」，不改会导致 LLM 即使有监控工具也只会翻文档。改为**证据优先级**表述：

```
你有两种证据来源，按需取用，不要偏废：
A. 活数据工具（query_metrics / list_active_alerts / search_logs / get_service_info /
   search_incident_cases）：回答「现在/最近发生了什么」「某指标是多少」「是什么原因」，
   优先用它。涉及现状的结论必须建立在工具返回值之上，不要编造数值。
B. 知识库工具（search_ops_knowledge）：回答「该怎么处置」「流程是什么」「有没有历史案例」，
   用它，并必须用 [编号] 标注引用。

典型排障顺序：先用活数据确认现象 → 再用知识库取处置步骤 → 给出现象+依据+步骤的完整结论。
工具返回 error 时换其它工具，或明确告知该数据当前不可用，不要假装查到了。
活数据来自示例数据源（source.mock=true）时，请在结论中说明「数据来源为演示数据」。
```

最后一句不能省 —— Mock 数据源是 v0.2 的默认形态，不声明就是欺骗用户。

## 6. SSE 协议与前端

现有 SSE 事件：`status` / `token` / `citations` / `done`。新增：

```jsonc
{"type": "tool_call",  "name": "query_metrics", "server": "monitor",
 "args": {"service": "order-service", "metric": "cpu"}, "mock": true}
{"type": "tool_result","name": "query_metrics", "ok": true,
 "summary": "cpu_usage_percent 近30min: avg 45.2 max 96.1 p95 93.4, 已超阈值 80%"}
```

设计约束：

- `tool_result` 只回传 **summary 单行摘要**（由 server 侧 `stats` 生成），**不回传完整数据点**，避免 SSE 帧过大。完整数据在后端日志里。
- 前端把它渲染成**可折叠的灰色气泡**（区别于对话正文），`mock: true` 时角标写「示例数据」。
- 引用卡片要区分两类来源：知识库引用（现状有，带 `[n]` 角标）与数据来源（`source.tool` + 采集时间）。**混为一谈会毁掉 v0.1 辛苦建立的引用可信度** —— 用户必须清楚哪句话来自文档、哪个数字来自监控。

| 场景 | 期望行为 |
|---|---|
| 未装 `langchain-mcp-adapters` | 启动正常，日志提示 `MCP 未启用：缺少依赖`，行为 = v0.1 |

## 9. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 工具变多导致 LLM 选错工具 / 不调工具 | 答案质量反而下降 | ① 工具控制在 7 个；② docstring 截断；③ SYSTEM_PROMPT 明确分工（§5.1）；④ 实测清单第 5 条盯着"多工具调用率" |
| 返回体过大挤爆上下文 | 超窗口、慢、贵 | 数据点硬上限 60、软默认 30；只回 statistical summary 给前端 |
| Mock 数据被误认为真实监控 | 演示失真，信任受损 | `source.mock` 字段 + 前端灰标 + 提示词强制声明 |
| MCP 服务挂掉拖垮主链路 | SSE 卡死 | §4.7 三层防护，重点是"错误返回文本不抛异常" |
| `ExceptionGroup` 报错难定位 | 排查耗时 | `format_exception_chain` 展开异常链写日志 |
| 与 OneCall 端口冲突（8003/8004） | 本地同时跑时抢占 | 本项目用 8101/8102，走环境变量可改 |
| 写操作工具被误引入 | 安全事故 | 工具名白名单 + 只读前缀校验（§4.4） |
